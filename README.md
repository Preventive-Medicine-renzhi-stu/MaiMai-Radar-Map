# 麦麦雷达地图 · mcd-radar-map

> 麦当劳程序员创意开发大赛（2026）参赛作品 · 基于麦当劳 MCP 开发

麦当劳的活动、上新、联名周边散落在 App、公众号和朋友圈里；同一样东西，几家门店的价格、排队和是否有货还不一样。等你想起「那个 9.9 元早餐」时，活动往往已经结束。

**麦麦雷达地图**把**麦当劳官方活动日历**、**你卡包里的优惠券**和**附近门店的实时状况**放到同一张地图上，按三种使用场景给出「现在该去哪家店」的明确答案。

- **目标用户：** 经常吃麦当劳、想又快又省又不踩空的人
- **项目形态：** 本地 Web 应用（地图 + 列表 + 日历 + 点餐闭环）+ 命令行工具
- **核心价值：** 把「翻 App 找活动 / 比门店」变成「打开地图，一眼看到答案」，再一路点到「取餐号」

**五个页面，一条完整链路：**

```
① 雷达地图 /            → ② 点餐 /order  → ③ 确认订单 /checkout  → ④ 下单成功 /result
                                                                   ⑤ 活动详情 /activity/:i
```

**怎么跑起来：** 双击 `start.bat`（Windows）/ `start.command`（macOS）即可 ——
自动建环境、装依赖、起服务、开浏览器，详见「三、安装 → 0. 一键启动」。

## 一、它解决什么问题

| 痛点 | 雷达地图怎么解 |
| --- | --- |
| 不知道最近哪家店、要走多久 | 模式一：门店按距离排布在地图上，点一下即画路径、给**步行 / 骑行 / 驾车**三种到达时长 |
| 只知道城市，不知道具体该定位到哪 | 顶部**定位输入框**：打地名 → 腾讯位置服务给 5 个候选 → 点一个即落点，门店 / 距离 / 时长 / 活动**整片跟着换** |
| 联名周边 / 限时新品上市就抢光 | 模式二：把活动与**各门店菜单**对齐，直接告诉你哪几家店有售 |
| 到了店才发现要排长队、想吃的还没货 | 模式三：先填要买的，再算「到达 + 取餐」总耗时，标出不可售商品 |
| 记不住活动时间 | 底部**未来 7 天活动日历**，点某天展开当天全部活动，再点进详情页 |
| 决定买什么时还得再打开 App 找商品 | 内建**点餐页**：左列分类 + 右列商品卡（图片 / 简介 / 价格 / 热量） |
| 不知道自己能省多少 | 底部购物车**实时结算**：自动配对券 + 积分换购，给出最省组合 |
| 下单后不知道几点能拿到 | 提交订单页给出**取餐号 + 预计到达 + 预计可取时间 + 前往餐厅路线** |

## 二、三种模式

### 1.1 就近 / 常客 —— 给普通就餐顾客

- 门店按**距离**或**我点过餐最多的店**两种口径排序，地图与列表联动
- 点击门店：地图自动规划**最近路径**，右侧显示门店编号、营业时间、预计到达、取餐方式
- 地图上的黄色大头针是当前推荐门店

### 1.2 追新 / 粉丝 —— 给想抢限时周边的麦麦粉丝

- 把限时活动文案与**每家门店的菜单**做匹配：`龙焰鸡腿堡三件套` 在 5 家店都有，`蘸酱韩式甜辣酱鸡块` 只有 3 家店有
- 侧边栏集中展示：**近期限时周边发售**、发售日期、**限时新品在哪几家店有售**
- 支持「全部 / 有商品 / 限时周边」三种筛选

### 1.3 极速模式 —— 又快、又饱、又省

1. **先填要买的商品**（可搜索、分类浏览、加减数量，实时显示合计与原价）
2. 系统对每家门店计算：**预计到达时长 + 门店繁忙度 + 取餐等待**，给出**最快取餐排行**
3. 对不利情况明确提示，例如：
   > 最近的门店是「麦当劳深圳赛西科技大厦餐厅」，但它在极度繁忙状态下预计要多等约 7 分钟；「麦当劳深圳南山书城餐厅」综合更快。
   > 「蘸酱韩式甜辣酱鸡块」该店菜单中暂无售
4. 同时推荐一个**极速套餐**（单码出餐、等待短、省得多）并**置顶你的历史订单**，列出原价 / 到手价 / 省多少，并附该门店可用的优惠券券码

### 未来 7 天活动日历

底部时间轴覆盖未来 7 天，每天显示活动条数与前两条标题，点击展开当天全部活动（含图片与正文），再点活动进入**详情页**（含关联餐品与「现在就点这份活动餐」入口）。

活动数据来自麦当劳 MCP 的 `campaign-calendar`。**注意**：2026 年该接口从 Markdown 文本换成了结构化 JSON
（`data.dailyList[].events[].articleDto{title,content,imgList}`），解析器已按新结构重写，
并保留对旧 Markdown / 通用键名的兼容 —— 否则会出现「活动页一条都没有」这种静默失败。

### 定位输入框：输入地点名 → 5 个候选 → 点一个即定位

城市下拉解决的是「换到哪座城」，**定位输入框**解决的是「换到城里哪个点」。后者的数据要好用得多：
同一个深圳，定位在「腾讯滨海大厦」和定位在「宝安机场」，门店、距离、到达时长、活动全都不是一套。

```
输入「人民广场」 ──▶ GET /api/suggest?keyword=人民广场&region=上海
                          │  服务端转发浏览器 Referer（命中腾讯域名白名单）
                          ▼
                 腾讯位置服务「关键词输入提示」ws/place/v1/suggestion
                          │  取前 5 条，每条自带 title / address / city / district / lat / lng
                          ▼
                下拉 5 条候选 ──点一条──▶ ① 地图立刻落到该坐标
                                         ② 城市 = 候选的 city，关键词 = 候选的 POI 名
                                         ③ 按新城市 + 新关键词重拉一次数据
                                            （门店 / 距离 / 步行驾车时长 / 抵达时刻 /
                                              活动日历 —— 一起换）
```

几处刻意的设计：

- **坐标是候选自带的**，选中即落点，不用再等一次检索 —— 也避免「先落城市中心、再飘到 POI」的跳动；
- **关键词用 POI 名而不是城市名**：`searchType=2` 下 `keyword` 越具体，MCP 返回的门店越贴近你要去的地方；
- **防抖 + 序号校验**：逐字敲键盘会连打十几次接口，前端 260ms 防抖、服务端 180s TTL 缓存；
  过期结果用 `seq` 丢弃，绝不把「上海的候选」画在「北京的输入框」下面；
- **失败就如实说**：腾讯返回 110（域名白名单）/ 121（配额）时，下拉里显示中文原因，
  **不会假装搜到**，也不会静默什么都不显示；
- **中文输入法安全**：组字期间（`compositionstart` → `compositionend`）不触发检索，且输入框与候选列表是**两个容器**，组字不会打断候选。
- **关键词不跨城市沿用**（线上踩过的坑）：候选是**程序自动填**进输入框的，它只属于所在的那座城市。
  若带着深圳的「深圳湾公园」去切北京，这个名字在北京查不到 → 返回 0 家门店 → 整座北京会被
  误判成「没有门店」。所以从城市下拉切城市时，**自动填的关键词一律丢掉**（并清空输入框，让界面与数据一致）；
  用户**手打**的则照用 —— 那是明确意图（例如填「海拉尔」再切呼伦贝尔）。
- **服务端还有一层兜底**：显式关键词仍然**第一个**试（不擅自改主意），但取不到就退回该城市的
  候选链继续试，不让一个失效关键词把整座城市堵死。换了词会在结果卡里写明
  「你填的 X 在这里查不到，已自动改用 Y」——不假装用的是你的词。

### 活动详情页：本地区能去哪几家店

活动页不只是一段文案 + 一张图。它现在会列出**当前地区可参与该活动的门店**，每家给出：

距离 · 步行 / 骑行 / 驾车三种时长 · **预计抵达时刻**（几点几分到）· 取餐等待 · 是否含该活动商品 · 一键「去这家点餐」。

## 二·五、点餐闭环

三种模式都只是「帮你决定去哪家店」。决定之后，点餐链路是完整可走通的：

### ② 点餐页 `#/order`

- **入口有三个**：首页左侧置顶的「一键点餐」区块、任意门店卡上的「去点餐」、右下角常驻悬浮球 🍔
- **「一键点餐」落在哪家店，由 1.1 决定**：在 1.1 里点过哪张门店卡片，就下哪一家；没点过则用 1.1 当前排序下的第一家（距离最近 / 最常去）。
  悬浮球上直接写着**将要下单的门店名**，不用点进去才发现店不对；置顶区块也会标明这家是「已选门店」还是「按距离最近推荐」
- **购物车一律从空开始**：进入点餐页不预选任何餐食，只对历史订单里出现过的商品打「你常点」标记
- 顶部横条是**当前点餐门店**：店名、地址、距离、预计到达、营业时间、取餐方式，右侧带 **「⇄ 临时换店」**
- 左上方**堂食 / 打包**切换
- **左列分类**（全部 / 折扣 / 门店真实标签）+ **右列商品卡**：图片、简介描述、现价与划线价、热量
- 点任意商品卡 → **详情弹窗**：官方套餐组成（`query-meal-detail` 的 rounds / 特调项）、营养网格（`list-nutrition-foods`）、并在弹窗里直接调数量加购
- 底部**悬浮购物车**：角标件数、实时应付、展开可看逐项明细

#### 临时换店（保留购物车）

点「⇄ 临时换店」弹出附近门店列表，每家标注**距离 / 到达耗时 / 取餐等待 / 繁忙度 / 可买 N/M 件**。
购物车按餐品码存储、与门店解耦，因此换店天然保住订单内容：

- 新店能买的 → 直接继续结算；
- 新店不卖的 → 保留在购物车、在抽屉里标 **「本店无售」** 并从金额中剔除，切回原店自动恢复。

### ③ 确认订单 `#/checkout`

桌面端为**两栏布局**：左栏放需要阅读的内容，右栏金额明细吸顶跟随，底部固定条显示总额与提交入口。

- 左栏：取餐门店（含「⇄ 换一家」）+ 就餐方式 + 预计到达 / 预计可取 → 商品清单（含每项热量）→ 优惠与积分
- **优惠券**：逐张标明「已使用 / 可用于部分商品 / 暂未匹配」，并显示券面价与有效期
- **积分换购**：见下方「积分是怎么算的」
- 右栏金额明细：商品小计 → 划线价合计 → 券抵扣逐条 → 积分换购 → 预计实付 → 共省

### ④ 下单成功 `#/result`

- **取餐号**（大字号）、订单号、下单时间
- **订单状态时间轴**：已下单 → 制作中 → 已出餐（按时钟推进，状态胶囊同步变色）
- **取消订单**：未出餐时可取消（二次确认后置为「已取消」）；**已出餐则按钮禁用并提示「无法取消」**
- 预计到达 / 预计可取时间
- **前往餐厅路线**小地图（腾讯地图不可用时自动降级为行程示意条）
- 页面提供 **「⏩ 演示：模拟已出餐」** 开关，方便评审一次看到「可取消 / 不可取消」两种状态

> ⚠️ 本项目只调用麦当劳 MCP 的**只读**接口，**不会真实下单或扣款**。
> 「取消订单」同样只在本地改状态，**不会调用 MCP 的 `cancel-order`**，弹窗里有明确说明。
> 正式支付仍需在麦当劳 App / 小程序完成。

### 顶栏用户信息

右上角是**用户信息入口**（头像 + 身份 + 可用积分），鼠标悬停、键盘 Tab 聚焦或点击都会展开下拉面板：

| 板块 | 内容 | 来源 |
| --- | --- | --- |
| 账号 | 登录身份（手机号脱敏 / 微信用户）、登录时间、退出登录 | 本地演示登录 |
| 积分账户 | 可用 / 累计 / 已过期，以及本月将过期、下月将过期、已使用、冻结 | `query-my-account` |
| 我的优惠券 | 卡包券 + 门店券，含券面价与有效期 | `available-coupons` / `query-store-coupons` |
| 历史订单 | 商品明细、门店、时间、实付金额 | `order-list` |
| 口味偏好 | 由历史订单的套餐子项推导出的常点商品 | 本地推导 |

> 🚧 **诚实边界**：麦当劳 MCP 的 35 个 Tool 里**没有昵称、手机号、头像**这类个人资料接口。
> 所以面板只呈现 MCP 真实返回的账户 ID（脱敏）、积分、券与订单，**不做虚构填充**，并在卡片底部明确写出这个缺口。
> 「账号」那一行是**本地演示登录**（见「九、隐私与合规」），与上面的真实数据各说各话、互不冒充。

### 省钱是怎么算的

- **券**：只使用券标题里**已写明**的规则。`kind=fixed`（如「¥9.9」）按券面价算差额；`free` 免单；`bogo` 免一份（需 ≥2 份）；标题未写金额的（如「麦旋风任选」）**只提示可用、不预估抵扣**。多张券做贪心配对，每张限用一次。
- **积分**：麦当劳的积分是「**积分 + 指定金额**」换购，**不是直接折现**。因此这里做的是「换购方案推荐」——找出积分够用、且购物车里正好有对应商品、且算下来更便宜的方案。
  - **按单份计价**：一次换购只替代 1 份商品，省的是「该商品单价 − 换购现金」。多份时不能拿整件总价去减，否则会把优惠算大。
  - **结合历史订单**：命中历史常点商品的换购方案会打上「你常点」并优先展示。
  - **积分不够也给路径**：列出「需 X 积分 · 还差 Y」，而不是直接隐藏。
- 最终金额一律以门店算价接口为准，页面上有明确标注。

## 三、安装

### 0. 一键启动（推荐：完全不碰命令行）

双击项目根目录的 **`start.bat`**（Windows，也可双击中文名的 `启动麦当劳雷达地图.bat`）
或 **`start.command`**（macOS）；Linux 下 `bash start.sh`。脚本会自动完成三件事：

1. 找到（或创建）虚拟环境 `.venv`；
2. 缺依赖就装 `mcp` + `python-dotenv`；
3. 起本地服务，并打开 <http://127.0.0.1:8770/index.html>。

打开后会先弹一个**登录框**（手机号验证码 / 微信扫码，均为本地演示登录，见「九、隐私与合规」），
不想登录可以点「暂不登录，先逛逛」。

> **这个本地服务不只是「静态托管」。** 它还提供 `/api/status`、`/api/city`、`/api/token`、`/api/suggest`，
> 让**换城市变成「点一下」**、**输入地名就能取候选**、**配 Token 也不用去命令行** —— 详见
> 「六、数据保真说明 → 城市下拉是怎么处理这件事的」与「二 → 定位输入框」。

### 0.5 版本控制与还原点

本项目用 Git 做基线管理。**主干 `main`，已打标签 `working-2026-10-10`**
（本机实测跑通的状态：城市实时切换 / 驾车路线 / 定位候选三项全通）。

```bash
# 回到这次跑通的版本（丢弃之后所有改动，执行前请确认）
git checkout working-2026-10-10

# 只看看当时某个文件长什么样
git show working-2026-10-10:web/view-radar.js

# 和基线对比改了哪些地方
git diff working-2026-10-10
```

⚠️ **这个仓库禁止推送到任何公开平台。** 原因：`web/data.js` 真实快照里含真实
`account_id` 与真实订单号（`.gitignore` 里已注明并给出脱敏换 `--demo` 的命令）。
配套防线：

- `.env`、`web/tmap-key.local.js`、`.venv/`、`.tmp/`、`.workbuddy/` **一律不入库**；
- `.gitattributes` 强制 `.sh` / `.command` 保持 LF（否则 macOS 终端报
  `\r: command not found`），并防止 Git 按平台改写换行符。

脚本可以带参数，例如换端口或强制离线快照：

```bash
start.bat --port 9000
bash start.sh --demo --no-open
```

> ⚠️ **同一个端口只会跑一个实例。** 重复双击启动脚本不会「多起一个服务」——
> 服务在监听前会先探一次 `/api/status`，发现已经有 `mcd-radar-local` 在跑就直接复用它
> （只把浏览器指过去）。这是必要的防线：Windows 的 `allow_reuse_address` 允许**两个进程
> 同时 bind 同一个端口**，一旦真的起了两个，两个实例会抢同一条连接，页面就会「时好时坏」。
>
> ⚠️ **换端口前请先补腾讯白名单。** 腾讯的域名白名单是按「host:端口」**精确匹配**的，
> 默认白名单里是 `127.0.0.1:8770`。一旦服务落到别的端口（例如 `start.bat --port 9000`），
> 就会出现「地图底图出得来、但门店坐标 / 驾车路线 / 定位候选全部取不到」——
> 脚本在端口顺延时也会把这句话打在控制台上。

### 1. 前置条件

- Python 3.10+

#### ⚠️ 坑一：域名白名单不接受带端口的来源

按腾讯官方 FAQ 的规则：**每行填一个裸域名**（不带 `http://`、不带端口），填 `example.com` 则子域名自动继承；**留空 = 不限制调用来源**。

实测确认（同一个 Key，只改 Referer）：

| 请求来源 | 结果 |
| --- | --- |
| `http://127.0.0.1/` | ✅ 放行 |
| `http://127.0.0.1:8770/` | ❌ `status:110 来源域名未被授权` |
| `http://localhost:8770/` | ❌ 同上（`localhost` 与 `127.0.0.1` 是**两个不同条目**，都要用就都加） |

也就是说，白名单里只写 `127.0.0.1` 时，**本项目默认的 `:8770` 端口会被拒**。三种解法任选：

- **最省事**：白名单**留空**（官方明确「留空则不限制调用来源」），或填 `*`
- ✅ **已实测可行**：把端口一起写进白名单，即四行都填上 —— `127.0.0.1` / `localhost` / `127.0.0.1:8770` / `localhost:8770`。
  官方 FAQ 没写这条，是实测出来的：**腾讯的匹配是「host:port 字面串」比较**，所以带端口的域名写在白名单里也认。本项目已按此配置验证通过（地点搜索 / 驾车路线 / 逆地址解析四接口均 `status:0`）
- 改用默认端口访问：`python -m src.main web --serve --port 80`，然后开 <http://127.0.0.1/index.html>

#### ⚠️ 坑三：GL JS 服务类库的 `Search` **没有 `search()` 方法**

这是最阴的一个坑——**接口明明通了，门店坐标还是取不到**。

腾讯 GL JS 的「服务类库」（`libraries=service`）里，`TMap.service.Search` 只暴露
`searchRegion` / `searchNearby` / `searchRectangle` / `explore` / `here` / `searchPoiId`，
**没有 `search()`**。写成 `svc.search({...})` 会抛 `svc.search is not a function`，
而这段代码在 Promise 里被 `catch` 静默吞掉，表现就是「不报错，但门店永远落在示意位置」。

正确用法：

```js
var svc = new TMap.service.Search({ pageSize: 5 });
svc.searchRegion({ keyword: keyword, boundary: 'region(' + city + ',0)' })
   .then(function (res) { /* res.result.data[].location -> { lat, lng } */ });
```

两个细节：① 参数名是 **`boundary`** 不是 `region`；② 边界串是 **`region(城市,0)`**，
末位 `0` 表示范围不足时自动扩页。注意 `Driving` 服务**确实**有 `search()`（`drv.search({from, to})`），
别把它一起改掉。

`tests/css_coverage.js` 已加静态防线：若 `map.js` 在 `Search` 实例上误调 `.search(`，体检直接报红。

#### ⚠️ 坑二：Key 的「权限」和「配额」是两回事

`JavaScript API GL`（底图渲染）与 `WebService API`（地点搜索 / 路线规划）的额度**分开计算**。勾了权限不等于有配额——实测 `X-Limit` 响应头里 `limit_pv=0` 时，接口会直接返回 `status:121`。

如果地图能出底图、但**门店落不了点、点门店画不出路径**，去控制台「配额管理」把 **地点搜索** 和 **驾车路线规划** 申请开通即可。

#### 常见报错对照

| 报错 | 含义 | 处理 |
| --- | --- | --- |
| `status:110 来源域名未被授权` | 白名单不含当前来源（注意端口） | 白名单留空 / `*`，或补上带端口的条目 |
| `status:121 此key每日调用量已达到上限` | 该接口**配额为 0** 或已用尽 | 控制台「配额管理」申请开通 |
| `status:199` | Key 未勾选 `WebService API` | 到 Key 设置里勾上 |
| 地图区域空白、控制台无报错 | 用 `file://` 双击打开（腾讯不支持） | 用 `--serve` 起本地服务，或直接用 WorkBuddy 预览 |

> 好消息是：以上任何一种情况都**不会白屏**。前端会退化为「门店按距离等比示意」或纯 SVG 距离雷达图，三模式与日历功能全部照常可用。

> 🔒 **为什么 Key 不写进 `data.js`？**
> 因为 `data.js` 是**要提交进仓库**的（让评审无需任何凭据即可打开页面查看完整效果），把 Key 写进去等于直接泄露。
> 因此 Key 单独落到 `web/tmap-key.local.js`，该文件已被 `.gitignore` 排除，**绝不会进入仓库**。

## 五、指标怎么算

**活动关注度**（`radar` 命令，用于活动排序）

```
关注度 = 时间基础分（今日 40 / 即将 25）
       + 临近加成（越近越高，最多 +10）
       + 亮点关键词（上新·联名·限量·买一送一·免费·抽奖…，最多 +30）
       + 可用券加成（活动文案命中你卡包里的券，+8）
```

**门店指标**（雷达地图，`src/geo.py`）

```
到达时长 = 距离 ÷ 交通方式速度（步行 80 / 骑行 260 / 驾车 500 米每分钟，按距离自动切换）
繁忙度   = 时段客流权重 × 门店因子（由门店编号稳定哈希得出）× 70 + 8
总耗时   = 到达时长 + 取餐等待
```

> ⚠️ **诚实性声明**：到达时长与繁忙度是**模型推算**，不是实时排队数据——麦当劳 MCP 不提供门店排队长度与经纬度。
> 前端所有推算值都带「预估」标注，并在模式三给出醒目提示。真实上线时把 `estimate_busy()` 换成真实叫号接口即可。

每段距离都同时给出**步行 / 骑行 / 驾车**三种估算（后端 `travel_options()` 一次算好，前端并排展示），
并标注哪一种是该距离下最推荐的方式 —— 走 200 米的人不需要看「驾车 1 分钟」，但想知道「骑车是不是更快」的人需要。
门店卡与活动详情页还会把时长换算成**预计抵达时刻**（「按现在出发，约 14:32 到」）。

### 城市下拉是怎么处理这件事的

分能力、不撒谎。下拉里每个城市都会标出它当下的状态：

| 角标 | 什么时候出现 | 点下去会怎样 |
| --- | --- | --- |
| 🟢 **当前快照** | 就是数据包所属的城市 | 无事发生（已经在这座城） |
| 🔵 **点一下切换** | 本地服务在线 **且** 已配置 `MCD_MCP_TOKEN` | 服务端带着 Token 去麦当劳 MCP **真实拉取**该城市数据，重写 `data.js`，随后页面自动刷新 |
| ⚪ **需先导出** | 没有本地服务（如纯静态托管、`file://` 打开），或没配 Token | **不假装切换**：地图视角移过去、清空门店标记，给出该城市地标的重新导出命令（带一键复制） |

三种情形的界面说明也会如实写在顶部状态条上：

| 情形 | 状态条右侧的小标 |
| --- | --- |
| 本地服务在线 + 有 Token | 🚀 本地服务已连接 · 点城市名可直接切换 |
| 本地服务在线 + 没 Token | 🔌 本地服务在线，但未配置 MCD_MCP_TOKEN · 无法实时切城市，并在下拉里**直接给出补填输入框** |
| 没有本地服务 | 📄 纯静态模式 · 换城市需重新导出 |

**「点一下切换」是怎么实现的**（这是本轮新增的能力）：

```
浏览器  ──POST /api/city {city, keyword}──▶  本地服务（127.0.0.1）
                                              │  用 .env 里的 Token
                                              ▼
                                    麦当劳 MCP（query-nearby-stores → 逐店 query-meals → …）
                                              │
                                              ▼
                                    重写 web/data.js + data.json
浏览器  ◀───────────── 页面自动刷新 ───────────┘
```

本地服务的全部接口（都只绑 `127.0.0.1`）：

| 接口 | 用途 | 说明 |
| --- | --- | --- |
| `GET /api/status` | 探测能力 | 返回 `{online, live, mode, live_reason, city, cities}`；`live=false` 时给出中文原因（如缺 `MCD_MCP_TOKEN`） |
| `POST /api/city` | 切城市 | 带 `{city, keyword}`，服务端用 Token 真实拉取并重写数据包；**失败绝不覆盖**已有数据 |
| `POST /api/token` | 补填 Token | 只写进 `.env`，不回显；过短的 Token 前端先拦一道 |
| `GET /api/suggest` | 定位候选 | 代理腾讯「关键词输入提示」，返回 ≤5 条带坐标候选；**服务端转发浏览器 Referer** 命中域名白名单 |

几条硬约束：

- 服务**只监听 `127.0.0.1`**，Token 永远留在服务端（`.env`），**不下发到浏览器、不回显**；
- 整趟要逐店拉菜单，实测一座 5 店的城市约 **8~15 秒**（门店多时会久一些），所以前端有一个带**秒表与步骤清单**的进度遮罩，而不是让你干等；
- **导出失败绝不覆盖**已有数据包 —— 特别是「返回 0 家门店」这种静默失败，会被当成错误抛出，
  页面会显示一张说清楚原因的错误卡，原有快照照常可看。

当然，命令行依旧可用（离线、CI、定时任务等场景）：

```bash
python -m src.main web --city 上海 --keyword 人民广场
python -m src.main web --city 北京 --keyword 国贸
```

`searchType=2` 时 MCP 要求 `city` + `keyword` 同时给，所以给个**该城市内真实存在的地点名**即可；
每个城市的默认地标词统一维护在 `src/cities.py`，并随数据包下发，前端不再硬编码第二份。

> **为什么冒烟测试读夹具而不是 `web/data.js`：** `web/data.js` 是真实数据包，
> 会被本地服务的 `/api/city` 直接重写 —— 你用网页切过一次城市，它就变成另一座城的数据了。
> 测试若直接读它，结果就取决于「上次导出的是哪座城市」，换座城市断言会**无缘无故变红**。
> 所以测试统一读 `tests/fixtures/demo-data.js`（由 `--demo` 快照生成的确定性数据）。
> 夹具缺失时 `web_smoke.js` 会明确提示 `python -m tests.make_fixture` 并退出（而不是静默跑错）。

> 冒烟测试会跑完整链路：**首屏登录弹窗（校验 → 登录 → 退出 → 换微信登录）** → 首页 →
> **一键点餐跟随 1.1 选中门店** → **城市下拉三态 / 本地服务探测 / 切换失败不伪装成功 / 补填 Token** →
> **定位输入框（候选渲染 / 方向键高亮 / 检索参数 / 搜不到如实说 / 点候选换城市）** →
> 悬浮球进点餐（购物车必须为空）→ 个人中心下拉 → 切堂食/打包 → 分类与**中文输入法搜索** → 加购 →
> **临时换店（验证购物车保留 + 本店无售剔除）** → 商品详情弹窗 → 结算页两栏 → 积分换购 →
> 提交订单 → 结果页取餐号 / 状态时间轴 → **已出餐拦截取消** → 取消订单 →
> **活动详情页（含本地区门店 / 距离 / 步行驾车时长 / 抵达时刻 / 去这家点餐）** → 返回地图。
> 其中包含七条**防回归断言**：
> ① 连点「＋」必须每次只 +1（守住事件委托的实现方式）；
> ② 换店后「可售件数 + 本店无售件数」必须等于购物车总件数（守住不静默丢单）；
> ③ 中文输入法组字期间，搜索框 DOM 节点必须**没有被替换**（守住「能打出中文」）；
> ④ 选了没有快照的城市后，`#radar-svg` 里不能残留别城的门店标记（守住不张冠李戴）；
> ⑤ 切城市失败后，当前城市**不能被偷偷改掉**（守住「不假装切换成功」）；
> ⑥ 定位检索搜不到时必须**明说没搜到**，不能渲染出一个空的下拉（守住「不假装搜到」）；
> ⑦ 切城市时**不能带上候选自动填的地名，但手打的关键词要照用**（守住「一座城被一个失效关键词堵死」）。

### 为什么还要一个真实浏览器测试

jsdom 不做布局，也不计算层叠上下文（stacking context），所以**「看得见但点不动」这类 bug 它测不出来** —— 冒烟测试会一直全绿。

真实踩过的坑：腾讯地图 GL SDK 会在 `#tmap` 内部注入一个 `z-index: 1000` 的绝对定位图层。`.map-area` 一旦不自建层叠上下文，这个 `1000` 就逃逸到根层叠上下文，压过登录弹窗（当时只有 `z-index: 140`）。地图因为白名单 / 配额问题没加载出来 —— 那层是**透明的**，肉眼看不出被盖住，但整块区域的点击全被它吃掉：**弹窗正常显示，所有按钮却点不动**。

两道独立防线（缺一不可）：

| 防线 | 位置 | 作用 |
|---|---|---|
| `isolation: isolate` | `.map-area` | 把地图 SDK 的 `z-index: 1000` 关在地图容器内部，不污染全局层叠上下文 |
| `z-index: 9000+` | `.switch-mask` / `.login-mask` / `#modal-host` / `.toast` | 即使别的第三方脚本再注入超高层级，弹窗依然在最上面 |

`tests/browser_hit_check.sh` 用真实 Chromium 内核做 `elementFromPoint` 命中测试，逐个确认弹窗上的输入框、按钮、tab 都是最高层元素；`tests/css_coverage.js` 做静态兜底，检查这两道防线没有被误删，同时守住**地图服务类库 API 名**（`Search` 实例误调 `.search(` 直接报红，见「坑三」）。

同一个脚本还顺手守住了**「地图落点」**这类同样"看得见但不对"的问题：

- **雷达首页**：切城市后地图视角必须落在目标城市（`MCD.map.debug()` 会吐出中心点与缩放级别）；
- **门店真实坐标**：`MCD.map.locate()` 会返回 `{ exact, located }`，`exact > 0` 表示门店拿到了腾讯的真实经纬度（否则是「按距离等比示意」）；
- **结果页「前往餐厅」小地图**：它曾经把基准点写死成深圳南山，切到呼伦贝尔下单后小地图照旧停在深圳 —— 与雷达页早先修掉的「切上海还停在深圳」是同一个 bug，只是漏改了这半边。现在两处都统一走 `cityCoord(数据包城市)`，`MCD.routeMap.debug()` 会吐出 `{ mode, routePoints, from, to }`：`mode === 'driving'` + 折点 > 2 才说明画的是真实驾车路线，而不是两点直线示意。
- **活动日历**：必须真的解析出活动条数（`7 天共 22 条`），因为**上游 MCP 换过返回结构** —— 见「坑四」；
- **定位候选**：点了候选之后地图中心必须等于候选自带的那对坐标（`31.232572,121.475242`），不能只是「看起来动了一下」。

### 坑四：MCP 把 `campaign-calendar` 从 Markdown 换成了 JSON

这是「深圳的活动怎么全没了」的真因，也是本项目最值得记的一条**静默失败**：

```text
旧返回（Markdown）              新返回（结构化 JSON）
## 2026-10-09                  {"data": {"dailyList": [
- 活动标题 A                       {"date": "...", "dateText": "...",
- 活动标题 B                         "events": [{"articleDto": {
                                      "title": "...", "content": "...",
                                      "imgList": [...]}}]}
                                 ]}}
```

老解析器只在 `_LIST_KEYS` / `_TITLE_KEYS` 里找通用键名，遇到新结构**一条都取不到，但并不报错** ——
页面于是安静地显示「活动 0 条」。修复方式是显式识别 `data.dailyList[].events[].articleDto`，
并保留对旧 Markdown 与顶层 `dailyList` / `data.events` 的兼容（`src/parsers.py` 的 `_daily_calendar` /
`_parse_activities_daily`）。

顺带修掉一个**状态误判**：无关键词的过去日期原本被当成 `upcoming`，现在改成
`_normalize_status(hint if hint != "upcoming" else "unknown", date_str, today)` —— 让日期说了算。

> 这类「上游悄悄改结构、下游静默归零」的坑，靠单元测试锁不住（测试用的还是自己的夹具）。
> 真正抓到它的是**真实浏览器测试打真实服务打真实 MCP**：断言「7 天日历里必须解析出 > 0 条活动」。

> 小提示：无头浏览器加 `--disable-gpu` 时，腾讯地图 GL 的**大头针图层**可能画不出来（底图与文字标签正常）。排查"标记不见了"时别用 `--disable-gpu`，否则会把渲染假象当成 bug。

## 九、隐私与合规

- Token 仅从环境变量 / `.env` 读取，仓库内**不含任何真实凭据**
- 地图使用**腾讯地图**（合规服务商）。代理模式下前端零密钥；即便启用 Key 模式，Key 也只落在本机 `web/tmap-key.local.js`（已 gitignore），**不会进入仓库**
- 不采集、不存储、不上传任何位置数据；历史订单仅用于本地展示
- `create-order` / `draw-lottery` 等**写操作一律不接入**，只读取公开的活动、门店、菜单与本人的券 / 订单

### 本地服务的安全边界

一键启动会拉起一个本地 HTTP 服务（`src/serve.py`），它的边界写死在代码里：

- **只监听 `127.0.0.1`**，不绑定 `0.0.0.0`，同网段的其他设备访问不到；
- Token 永远留在服务端（`.env`），**不下发到浏览器、不在响应里回显**；
- 页面上的 Token 输入框只是把值转发给本机服务，由服务写进 `.env`；**浏览器不保存它**
  （`.env` 已被 `.gitignore` 排除）；
- 切换城市走的是 MCP 的**只读**接口，不会下单、不会扣款、不会消耗积分。

**会被真实 MCP 数据覆盖**的文件 —— 用带 Token 的本地服务切一次城市，它里面
